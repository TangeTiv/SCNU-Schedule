## 0. 文档目的

本次讨论要解决的问题：**在【校园】页后续加一批功能**（二手集市、课程/老师评价、学习树、美食街、AI 审核），
以及为它们准备**登录能力**。

讨论中发现一个关键事实：**这批功能里有 4 个是 UGC 社区平台，1 个是审核机制，
它们全部需要服务端。** 而本项目目前是**纯单机 App**。
所以这不是"加几个页面"，而是一次**架构级转向（单机 App → C/S 平台）**。

本文档把这个转向拆成可分别推进的阶段，并明确每阶段的边界、风险与依赖。

## 2. 目标形态

```
现在：  用户 → Android App → (本地 Room/DataStore) + (SCNU 教务爬取)
目标：  用户 → Android App → 本地（课表/凭据/缓存）
                          ↘ 云开发后端（账号 / 社区内容 / 审核 / 举报）
```

**保持不变的原则（重要）**：
- 课表、今日、设置、桌面小组件**继续离线优先**，不依赖网络与登录。
- SCNU 教务的**客户端爬取**方式不变（这是本项目已有的稳定能力）。

## 3. 身份与会话体系（核心）

> **术语澄清（重要）**：**身份只有一个** —— "华南师范大学 X 级学生，学号 2024xxxx"。
> 用户只输入一次学号密码，只有一个登录入口。
>
> 所谓"两个"，指的是**两个会话**：教务系统签发的 Cookie 会话，与你自己服务器签发的 token 会话。
> 这不是设计选择，是**技术事实**——教务 Cookie 只对 `*.scnu.edu.cn` 有效，
> 你的服务器**既收不到、也无权验证**它，因此必须自己签发 token。
>
> 本文档早期版本用"两种身份"表述，容易让人误以为要注册两遍，现统一为"一个身份、两个会话"。

### 3.1 两个会话必须分开

| | 教务会话 | 社区会话 |
|---|---|---|
| 凭据 | 学号 + 密码 | 社区账号 + 登录 token |
| 存放 | **仅本地**（Keystore 加密） | 服务器 |
| 用途 | 教务同步 / 选课 / 成绩 / 考试 / 学业情况 | 发帖、评论、举报 |
| 服务器可见 | **学号**（不含密码） | 账号、学号（加密存储） |

**硬约束**：教务密码**永不上传服务器**。
理由：让社区服务器持有全校学生的统一身份认证密码 = 学校级安全事故
（华师统一身份认证通常还关联邮箱、VPN、图书馆、财务）。

### 3.2 教务会话（本地）

- 存储：Android Keystore 生成 AES-GCM 密钥 → 密文写入 DataStore。
- 解锁：`BiometricPrompt`（见 §4.3 的技术矛盾与折中）。
- 生命周期：会话缓存于内存（`ScnuCookieJar`），设有效期，超时重验生物识别。

### 3.3 社区会话（远端）

- 服务器侧账号表：`user_id` / `username`（前台显示）/ `student_id_enc`（加密学号）/
  `created_at` / `status`。
- **前台只显示自定义用户名**，不显示学号、不显示真实姓名（后台实名、前台自愿）。
- 登录凭证：token（服务器签发，客户端存 Keystore 加密区）。

### 3.4 绑定流程（按你确定的方案）

```
① 用户在【我的 → 账号】输入学号 + 密码
② App 本地调用教务统一身份认证（复用现有 ScnuSsoLogin 逻辑）
   ├ 成功 → 本地"开锁"，标记"已验证华师学生"
   └ 失败 → 提示错误，不解锁
③ 用户首次进入社区功能 / 首次发帖
   → 上报【学号 + 自定义用户名】到服务器，换取社区 token
   → 密码全程不出设备
```

### 3.5 已知风险与残余风险（本期**不加固**，明确记录）

你已决定：**先按上述思路完成，暂不考虑改包问题。** 记录在案，供后续决策：

1. **服务器无法验证学号真实性**。"本地开锁"是客户端状态，服务器只收到一个学号字符串。
   改包 / hook / 直接调 API 即可伪造任意学号。
2. **学号格式可枚举**。项目自身代码即记录该规则：
   `ScnuAcademicScraper` 注释「学号形如 `202421315041`，前 4 位即入学年」。
3. **冒名风险 > 混入风险**。他人用某学号发帖，责任归属该学号本人，
   涉及名誉权，比匿名发帖严重。

**后续可选加固阶梯**（成本从低到高，留作 P2 之后按需启用）：

| 手段 | 效果 | 成本 |
|---|---|---|
| 邀请码 / 学号白名单 | 防批量注册，最便宜有效 | 纯运营，近零 |
| 学号唯一绑定、不可改 | 防一人多号刷屏/自评 | 低 |
| 上报教务页面的学籍片段（姓名/学院/年级） | 伪造成本从"填数字"升到"伪造教务页面" | 低 |
| 挑战-响应（服务器发 nonce，回传含学号的教务接口响应） | 服务器可确认会话真实性 | 中 |
| 服务器代理登录 | 彻底防伪造 | ❌ 已否决（服务器将持有全校密码） |

## 4. P0：登录与凭据复用

> **特点：不依赖任何后端决策，可立即并行开工。**

### 4.1 目标

1. 消除"每次进教务模块都要重输学号密码"的重复输入。
2. 统一两套并存的登录实现。
3. 在【我的】页提供"账号"入口，支持查看状态与退出登录。
4. **不引入全 App 门禁**：课表 / 今日 / 设置保持免登录可用。

### 4.2 模块划分（建议）

| 模块 | 职责 |
|---|---|
| `data/auth/CredentialStore` | Keystore + AES-GCM 加解密；DataStore 读写密文 |
| `data/auth/ScnuAuthManager` | **合并** `ScnuScraper.login` 与 `ScnuSsoLogin.login`，对外暴露单一 `login()` / `ensureSession()` / `logout()` |
| `data/auth/AuthStateRepository` | 暴露 `StateFlow<AuthState>`（未登录 / 已登录 / 凭据失效 / 锁定） |
| `ui/account/AccountScreen` + `AccountViewModel` | 账号页（`Destination.Account`） |

### 4.3 关键设计：生物识别与静默重登的矛盾

`KeyGenParameterSpec.setUserAuthenticationRequired(true)` 会使密钥**只能在用户认证后的短授权窗口内使用**，
导致**后台静默重登失败**。

**折中方案（推荐）**：
- 生物识别只保护**取用凭据那一刻**（`BiometricPrompt` + `CryptoObject` 解密）。
- 取到后把会话缓存到内存，设有效期（建议 **15 分钟**）。
- 超时后再验一次指纹。
- 效果：进教务功能验一次，随后连续操作不再反复验证。

### 4.4 关键设计：凭据失效与失败锁定

- **密码会变**：华师可能强制定期改密 → 必须做"凭据失效 → 引导重输"的完整流程。
- **失败锁定**：SSO 连续失败会锁账号 → **禁止无脑重试**，失败 N 次后进入冷却期并提示用户。
- **风险告知 + 一键清除**：账号页明示"root / 定制 ROM / 备份提取仍可能拿到密文"，并提供一键清除。

### 4.5 需要改动的现有文件（预估）

| 文件 | 改动 |
|---|---|
| `data/network/ScnuScraper.kt` | 登录逻辑迁出，保留爬取职责 |
| `data/network/selection/ScnuSsoLogin.kt` | 成为唯一登录实现（消化掉 TODO） |
| `ui/campus/CampusSyncViewModel.kt` | 改用 `ScnuAuthManager`，去掉手输凭据 |
| `ui/campus/CourseSelectionViewModel.kt` | 同上 |
| `Navigation.kt` | 新增 `Destination.Account` |
| `MainActivity.kt` | `ScreenContent` 注册 `Destination.Account` |
| `ui/settings/SettingsScreen.kt` | 新增"账号"入口 |
| `data/di/NetworkModule.kt` | 若引入社区 HTTP 客户端，新增 `@Named("cloud")`（**不得复用 scnu 的 CookieJar**） |

## 5. P1：后端方案

### 5.1 选型：腾讯云 CloudBase（云开发）

你已确定走云开发。选它的理由：

- 免运维，自带**云函数 + 云数据库 + 云存储**。
- **默认域名自带备案**——这是国内"低成本 + 可对外服务"目前最省事的解法。
- 有免费额度，先用免费额度验证，用户量起来后再升级或自建（符合你的规划）。
- **同厂生态**：内容安全（TMS/IMS）同属腾讯云，接入方便，有免费额度。

### 5.2 需要提前知道的代价

| 代价 | 说明 |
|---|---|
| **云数据库是文档型**（类 MongoDB），不是 MySQL | 有关系的数据（用户–课程–评价）需按文档模型设计（冗余 / 聚合），不能直接 join |
| **云函数是 Node.js** | 后端语言与 Android/Kotlin 不同，需要额外学习成本；但 AI 审核 SDK 生态以 Node 最成熟 |
| **免费额度有限** | 到期或超额需升级；**绝不能让用户数据存在随时会消失的机器上** |
| 数据库/存储导出受限 | 需提前规划导出方案，避免被厂商锁定 |

### 5.3 数据模型草案

```
users           { _id, username, student_id, status, created_at,
                  device_id, reg_ip, reg_at }              // 注册留痕（§5.6）
settings        { _id, key, value }                        // 含 registration_open 全局注册开关
courses         { _id, kch, kcmc, jsxm, xf, kcxzmc, kkbmmc, review_count }
reviews         { _id, course_id, user_id, username_snapshot, content,
                  tags[], status(pending/visible/hidden/rejected),
                  report_count, created_at }
reports         { _id, target_type, target_id, reporter_id, reason, created_at }
moderation_log  { _id, target_id, action, actor, reason, created_at }   // 留存 ≥6 个月
```

> `courses` 是**共享课程目录**，由用户上报的课程元信息众包生成（见 §6.2）。
> `username_snapshot` 冗余存用户名，避免读列表时 join users。

### 5.4 API 草案

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/bind` | 学号 + 自定义用户名 → 换取 token（**先校验全局注册开关 + 同设备限流**，见 §5.6） |
| POST | `/courses/report-meta` | 上报课程元信息（众包课程目录） |
| GET | `/courses/search?q=` | 课程目录搜索 |
| GET | `/courses/{kch}/{jsxm}/reviews` | 某老师的某门课的评价列表 |
| POST | `/reviews` | 发布评价（含机器初筛） |
| POST | `/reviews/{id}/report` | 举报 |

### 5.5 可迁移性约束（**重要**）

为避免被云厂商锁定、确保以后能搬到自建服务器：

- 业务逻辑**不写进云开发特有 SDK**，API 层自己包一层薄适配器。
- 数据模型用**标准语义**（对象存储 / 集合），不依赖厂商私有特性。
- 目标：以后换服务器是**搬家**（改适配器 + 导数据），不是**重写**。

### 5.6 注册准入：最低防护（已定）

**已定**：**不做邀请码**，但保留三条零成本的最低防护。

#### 决策背景（重要，避免后续被误读）

用户的原始推理是：「软件没有注册通道，只要是华师学生就有统一身份认证账号，所以不需要邀请码」。

**该推理有一个前提不成立**：**服务器看不到"通过 SSO"这个动作**。

因为采用「本地验证 + 上报学号」（§3.5），服务器**只收到一个学号字符串**，
**无法验证其真伪**。因此：

> **客户端有门槛 ≠ 服务器有门槛。**
> 没有邀请码时，**服务器侧实际不存在任何准入控制**——
> 改包或 hook 即可伪造任意学号注册。华师有计算机学院，这不是理论风险。

此外，法律上的"面向公众"指「**面向不特定的多数人**」，
华师约 4 万学生属不特定多数，**"只要是华师学生就能注册"仍属面向公众**，
ICP 备案要求依然存在。

#### 最终采用的三条最低防护

| # | 措施 | 作用 |
|---|---|---|
| 1 | **全局注册开关**（后端 flag） | 出问题时能**一键停止注册** |
| 2 | **同设备 / IP 注册数限流** | 挡住脚本化批量注册 |
| 3 | **注册留痕**（设备指纹 + IP + 时间） | 事后可追溯、可批量封禁 |

> 未来若需要收紧，**邀请码可作为增量方案**（代码改动很小：`users` 加一次校验即可），
> 届时无需重构。

#### 已记录的残余风险

- 服务器侧**无法区分真实注册与伪造注册**。
- 恶意用户可冒用他人学号注册并发帖，**责任归属该学号本人**（冒名风险，§3.5）。
- 只能靠**事后追溯 + 封禁**处理，无法事前拦截。

### 5.7 学号存储：明文（已定）

**已定**：学号在服务器上**明文存储**，不做加密。

**需要一并遵守的低成本约束**（与加密与否无关，都是 PIPL 要求）：

- 隐私政策**仍须明示**"收集并存储学号"及用途。
- **前台只显示用户名**，学号**不返回给客户端**（§3.3 已定）。
- **日志中不得打印学号**。
- ⚠️ **云开发数据库绝不可开"公开读"权限** —— 这是最常见的事故来源。
- 传输走 HTTPS（云开发默认满足）。

**已记录的残余风险**：若数据库泄露，泄露的是「**学号 ↔ 用户名 ↔ 评价内容**」的对应关系。
学号本身敏感度中等（不像身份证号可直接用于身份盗用），
但与发帖内容关联后即成为"某人说过什么"的证据，这是风险的主要来源。

## 6. P2：首个社区模块 —— 课程 / 老师评价

> 选它作为首个模块的理由：纯文本、结构简单、合规压力最小，
> 且能**复用教务已有的课程与教师数据**。

### 6.1 锚点：`kch + jsxm`

- 口径 = 「**某位老师的某门课**」，与你的需求完全一致。
- 数据来源 = `GradeEntity` 的 `kch`(课程代码) + `jsxm`(任课教师)。
- **上传时只传课程元信息，绝不上传成绩**（`cj` / `jd` 属隐私）。

### 6.2 课程目录冷启动（众包）

```
用户同步成绩 → 本地已有 kch + kcmc + jsxm + xf + kcxzmc + kkbmmc
            → 上报这些元信息（不含分数）
            → 服务器去重合并 → 形成共享课程目录
```

好处：**零额外录入成本**、数据来源权威（教务下发）、天然完成冷启动。

### 6.3 交互设计：双入口（已定）

**核心判断**：本模块的主场景是「**选课前先调研**」——看的人远多于写的人。
因此**看**与**写**拆成两个入口，各管一件事：

| | 入口 A · 搜索 | 入口 B · 我的课程 |
|---|---|---|
| 谁能用 | **登录即可**（含未修过的人） | 仅已修 / 在修 |
| 能做什么 | 看评价、看标签、看评价数 | 写评价 |
| 数据源 | 服务器课程目录 | 本地 `grades` / `academic_courses` |
| "新建课程条目" | 不涉及 | 缺条目时**自动上报**，用户无感 |

**搜索粒度必须精确到 `kch + jsxm`**（课程 + 老师），
因为同一门课不同老师的评价不可混。

> ⚠️ 若只做"搜索"单一入口：未修过的课无法"新建条目"，
> 且用户需**手填**课程名/老师 → 异体字与错写会产生**重复课程条目**、后期无法合并。
> 双入口从根上避免这个问题。

### 6.4 "已修 / 在修"判定（已定）

数据来源（**都在本地，无需额外开发**）：

| 来源 | 字段 | 含义 |
|---|---|---|
| `GradeEntity` | 有成绩 | 已修 |
| `AcademicCourseEntity` | `readStatusCode = 4` | 已修 |
| `AcademicCourseEntity` | `readStatusCode = 1` | **在修** |

**已定规则**：

- **已修** → 可写全部标签。
- **在修** → **也可写**，但：
  - 卡片打「在修中」角标；
  - **「给分」类标签不可选**（成绩尚未出，评价不准）。
- **未修** → 只读，不能写。

**前置条件提醒**：用户必须先**同步过成绩或学业情况**，否则本地无已修/在修记录，
一条都写不了。需要明确的引导文案（"你还没同步过成绩，先同步一下"）。

### 6.5 防刷与编辑（已定）

- **同一用户对同一 `kch + jsxm` 只能写一条，但可随时编辑**。
- 前台只显示自定义用户名，不显示学号与真实姓名。
- 服务器无法验证"用户真的修过这门课"，只能靠客户端声明（与 §3.5 同源问题）。

### 6.6 搜索的技术实现（待优化项）

云开发是**文档数据库**，对 `kcmc` 直接上正则模糊匹配会**全表扫描**、性能差。

**建议**：为课程条目额外维护一个**检索字段**（分词 + 拼音），例如
「编译原理」→ `编译 原理 编译原理 bianyiyuanli byyl`，搜索时对该字段做匹配。

### 6.7 老师维度聚合（可后置）

`courses` 表已有 `jsxm`，因此"这位老师教过哪些课、各有多少评价"在**数据结构上现在就能支持**，
UI 可以后续再做，不阻塞首个版本。

### 6.8 UI 与导航挂载

- 【校园】页新增卡片（挂 `TertiaryServiceGrid` 的两个预留位之一，复用 `SmallServiceCard`）。
- 新增 `Destination`：`CourseReviewList(kch, jsxm)` / `CourseReviewEditor(kch, jsxm)` 等，
  并在 `MainActivity.ScreenContent` 注册。

### 6.9 本地缓存（Room）

- 新增缓存表（如 `cached_reviews`）→ 支持离线浏览、减少请求。
- ⚠️ **Room 版本升级需写 Migration**（`app/schemas/` 有 schema，勿破坏）。

### 6.10 设计红线（已定）

1. **不做量化评分（1–5 星）**（**已定**）。量化评分 + 排名更易被认定为"损害名誉"，
   也最易引发教师投诉。改用**标签 + 文字**——这些是**客观描述**，法律风险低得多。
2. **定位为"学习方法 / 攻略"而非"评价老师"**（保持你原始描述里的定位）。
3. **禁止人身攻击**：涉及"师德""人品"等词进待审队列。
4. **前台只显示自定义用户名**，不显示学号与真实姓名。

### 6.11 标签清单（已定稿）

**设计原则**：标签必须描述**课程与教学事实**，不描述**老师个人**。

| 维度 | 选项 | 谁能选 |
|---|---|---|
| 课程难度 | 轻松 / 一般 / 偏难 / 很硬核 | 已修 + 在修 |
| 作业量 | 几乎没有 / 适中 / 较多 / 很多 | 已修 + 在修 |
| 点名频率 | 从不 / 偶尔 / 经常 / 每节都点 | 已修 + 在修 |
| 考核方式 | 期末笔试 / 开卷 / 论文报告 / 小组作业 / 实验实践 / 平时为主 | 已修 + 在修 |
| 课程收获 | 收获很大 / 一般 / 学不到什么 | 已修 + 在修 |
| **给分情况** | 给分宽松 / 给分正常 / 给分偏严 | **仅已修** |

**交互规则**：

- 每个维度**单选**（不是多选）→ 便于统计出分布
- 所有维度**都可留空**，不强制填满
- **展示时按维度聚合**，例如「**60% 的同学认为给分宽松**」，
  而不是逐条罗列 —— 这比单条评价更有参考价值，且呈现的是**群体分布**而非个人指控，
  **法律风险显著更低**

**明确不设标签位的类型**（只能出现在正文，且命中敏感词进待审）：

- 涉及老师个人：师德、人品、态度、口音、外貌、性格
- 对具体个人的指控性描述

**首版不提供自定义标签**：避免标签失控与审核成本上升。

## 7. 审核机制（先发后审）

已确定：**机器初筛 + 举报**（不做全量人工复核）。为弥补合规缺口，补三条低成本措施：

1. **敏感词前置拦截**（不是只做标记）：命中直接进待审队列、**不展示**。
2. **举报达阈值自动隐藏**：如 3 人举报 → 自动下架待你确认。解决"你不在线时没人管"。
3. **教师申诉通道 + 日志留存 ≥6 个月**（法规要求）。申诉通道是重要的"尽责"证据。

**工具建议**：腾讯云**内容安全 TMS**（文本），后期加 **IMS**（图片，用于美食街/二手集市）。

**残余风险**（明确记录）：纯机器初筛缺"人工复核"环节，
《网络信息内容生态治理规定》要求平台对用户发布信息进行审核。
校内小范围 + 邀请码白名单 + 纯文本的前提下，MVP 阶段可接受，但**最坏情况**（严重诽谤内容未及时处理）责任难以免除。

## 9. AI 功能设计

### 9.1 关键前提：BYOK（用户自带 API Key）

**已定**：用户自己填 API Key，不建官方 AI 网关。

**为什么这个决定很重要**：

| 好处 | 说明 |
|---|---|
| 零成本 | 无账单风险，不需要配额/限流/计量系统 |
| 合规更干净 | 数据由用户设备**直接发给他自选的模型厂商**，开发者不经手、不存储 |
| **不阻塞 P1** | 不需要云函数网关 → **AI 功能可与 P0 并行或紧随其后开工** |
| 机制复用 | 用户 Key 与教务密码**共用同一套 Keystore 加密存储** |

**代价**：**体验门槛高**。让华师学生自行注册厂商、充值、生成 Key、粘贴进 App——
**绝大多数人做不到**。此功能的成败**取决于引导做得好不好，不取决于代码**。

**必须配套的 5 件事**（缺一件 = 这个功能等于没人用）：

1. **图文教程**：分步截图教"去哪注册、在哪生成 Key、怎么充值"
2. **厂商预设模板**：**只放「DeepSeek」+「自定义」两项**（已定，见 §9.1.1）
3. **统一走 OpenAI 兼容格式**（`/v1/chat/completions`）
4. **一键测试连通性**：填完立刻验证"可用 / 不可用 + 原因"
5. **抽象 `AiProvider` 接口**：不写死 OpenAI client，以后接官方网关时不必重写

> ⚠️ **API Key 绝不打进 APK**。BYOK 下 Key 存在用户设备（Keystore 加密），
> 这是唯一可接受的形态。若将来做官方通道，Key 必须只存在云函数中。

#### 9.1.1 厂商预设：DeepSeek + 自定义（已定）

**只做两项**，不铺开多厂商，降低维护成本。

**为什么这个简化是安全的** —— 已核实 DeepSeek 官方文档（2026-09-22）：

| 模型 | Tool Calls | 图像理解 | 上下文 | 价格（元/百万 token，空闲时段） |
|---|---|---|---|---|
| `deepseek-flash` | ✅ 支持 | ✅ 支持 | 1M | 输入 1 / 输出 4 |
| `deepseek-v4-pro` | ✅ 支持 | ❌ 不支持 | 1M | 输入 4.5 / 输出 13.5 |

**关键结论**：

- **两个模型都支持 Tool Calls** → 之前担心的"预设模型不支持工具调用"**在 DeepSeek 路径上不存在**。
  §9.2 的降级策略因此**只对「自定义」接的第三方模型生效**，属于安全网而非常见路径。
- **base_url（OpenAI 格式）**：`https://api.deepseek.com`
- **模型名**：`deepseek-flash`（推荐，便宜） / `deepseek-v4-pro`
  （旧名 `deepseek-v4-flash` 仍可调用但已下线，会被路由到 V4.1-Flash 按 Flash 计费）
- ⚠️ **有「空闲 / 高峰」分时定价**：北京时间工作日 9:00–12:00、14:00–18:00 为高峰，
  价格为空闲时段的两倍。做成本提示时要说明。
- ⚠️ **有思考模式**：课表问答这类任务应**显式关闭思考模式**，降低延迟与成本。
- ⚠️ **单点依赖**：只预设一家，若 DeepSeek 故障或涨价，用户没有备选。
  但有「自定义」兜底，风险可控。

**「自定义」项必须让用户填全**：`base_url` + `model` + `key`，
并**明确提示**"需支持 OpenAI 兼容格式与 Tool Calls，否则只能回答摘要类问题"。

### 9.2 首个 AI 功能：本地数据问答助手

**已定**：首版**尽量全覆盖**本地数据。

#### 入口形态（已定）

**AI 是【校园】页的一个独立模块**——像「教务同步」「成绩查询」那样，
在【校园】页挂一张卡片，点进去是一个独立的 AI 对话页。
（**不是**每个模块内嵌一个 AI 入口。）

**代价与对策**：全局入口意味着"用户可能问任何模块的事"，
若把全部工具塞进 prompt 会失控（详见 §9.6）。对策是**按意图路由、只加载命中的工具组**：

```
用户进 AI 页
  → 默认只加载【教务组】（课表/考试/成绩/学分，约 5 个工具）
     理由：入口在【校园】页，用户最可能问教务
  → 规则命中"二手/卖/买/交易" → 换【二手组】（3 个）
  → 规则命中"美食/吃/店"     → 换【美食组】（3 个）
  → 命中跨模块（如"没课 + 交易"）→ 加载 2 组（6 个，仍可控）
  → 未命中 → 走 Agent 兜底，但只带**当前已加载的组**，绝不带全部
```

**工具数因此始终 ≤ 6**，不随模块数量线性膨胀。

> ⚠️ 入口在【校园】页会让用户**默认以为"这是教务相关的 AI"**，
> 所以页面上的**引导卡片**（"问问课表""问问考试""问问学分"）在这里作用更大：
> 既明确意图，也把"这个 AI 能回答什么"讲清楚。

#### 覆盖范围

| 数据 | 用户会问 | 谁来处理 |
|---|---|---|
| 课表 | "明天有几节课""周三下午有课吗" | 本地查询 |
| 考试 | "下周期中在哪考""还有几门没考" | 本地查询 |
| 成绩明细 | "高数考了多少分" | 本地查询 |
| 学分 / 绩点 | "还差多少学分毕业""绩点多少" | 本地**计算** |
| 培养计划 | "还差哪几类学分" | 本地**遍历树汇总** |
| 非正式学时 | "非正式学时够了吗" | 本地查询 |

#### 核心设计原则：让模型只做"翻译"，不做"检索"和"计算"

这是**防幻觉的关键**：

- **检索与计算交给本地代码**（确定性）：学分汇总、绩点、树遍历全部由 Kotlin 算好。
- **模型只负责把结构化结果翻译成人话**（不确定但无害）。
- 若让模型自己去读整棵培养计划树并做汇总，几乎必然算错。

#### 上下文分层（因为"全覆盖"不等于"全塞进 prompt"）

```
基础层（必做，任何模型都能用）
  └ 注入精简摘要：本周+下周课表 / 未来考试 / 学分与绩点统计
增强层（模型支持 tool use 时启用）
  └ 本地查询函数：查某天课程明细 / 查某门课成绩 / 查培养计划进度
```

- **为什么不能全塞**：成绩明细 + 培养计划树 + 非正式学时全部序列化后 token 量很大，
  且**上下文越长，模型注意力越分散、准确率越低**。
- **"全覆盖"靠按需查询实现，不是靠堆 prompt。**

> ⚠️ **风险**：`function calling` **不是所有模型都支持**。BYOK 下用户可能选到不支持的模型。
> **对策**：填 Key 时**检测 tool use 能力**；预设模板中**标注**哪些厂商支持；
> 不支持时**降级**为基础层，并明确提示用户"换用 DeepSeek / 通义可获得完整体验"。

#### 路径策略：规则前置 + Agent 兜底（已定）

**纯 Agent 的问题**：慢（每问都要多轮往返）、不稳（模型可能选错工具）、
且**不支持 tool use 的模型完全用不了**。

**因此采用双路径**：

```
用户提问
  ├ 规则命中（课表 / 考试 / 成绩 / 学分 等明确意图）
  │    → 本地直接查好 → 交给模型翻译
  │      优点：零成本、零延迟、100% 准确、任何模型都能用
  └ 规则未命中（模糊 / 组合 / 需要明细）
       → 走 Agent 循环，让模型自己选工具
         优点：灵活；代价：慢、依赖模型能力
```

**规则前置能把约 80% 的提问压成"一次调用"**，体验提升显著。

> 注意：用户描述的"识别到课表、下周课表就调工具"**本身就是规则能做的**。
> Agent 的价值在于处理规则覆盖不到的模糊提问（如"我这学期是不是比上学期累"）。

#### Agent 循环与本地工具集

```
用户提问 → LLM（带工具清单）→ 需要工具？
                                 ├ 是 → 本地执行工具（读 Room）→ 结果回传 → LLM 再决策
                                 └ 否 → 直接生成回答
```

**工具清单**：

| 工具 | 参数 | 典型提问 |
|---|---|---|
| `get_courses_by_date_range` | `start_date`, `end_date` | "明天有什么课""下周课表" |
| `get_exams` | `only_upcoming` | "下周期中在哪考""还有几门没考" |
| `get_grades` | `course_name`（可选） | "高数考了多少分" |
| `get_credit_summary` | 无 | "还差多少学分""绩点多少" |
| `get_plan_progress` | `category`（可选） | "还差哪几类学分" |

> **经验**：工具的 `description` 文案质量**直接决定模型选得对不对**。
> 最有效的写法是**在描述里写清"用户会怎么问"**，例如
> 「当用户问"明天有什么课""下周课表""这周三下午有课吗"时调用」——
> 远比写"获取课程数据"准确。

#### 必须处理的五个坑

| # | 坑 | 对策 |
|---|---|---|
| 1 | **模型能力差异**（最大不确定性） | 差模型会选错工具、参数格式错、反复调同一工具不收敛，或干脆不调直接瞎编 |
| 2 | **循环失控** | 设**最大工具调用轮数 = 5**（已定），防死循环烧用户的钱 |
| 3 | **过程反馈**（UX 硬要求） | 工具调用期间必须显示"正在查询你的课表…"；3 轮工具 = 4 次 API 请求，等待明显更长 |
| 4 | **参数校验**（安全） | 日期格式、课程名长度等**必须校验**，不能让模型传什么就执行什么 |
| 5 | **降级** | 见下方"降级策略" |

#### 降级策略（已定）

模型不支持 tool use 时：**自动降级**到「规则直查 + 摘要注入」模式，
并在界面提示「当前模型不支持工具调用，建议换用 DeepSeek」。

> 注：DeepSeek 两个模型都支持 Tool Calls（见 §9.1.1），
> 因此本降级路径**实际只对「自定义」接入的第三方模型生效**，属安全网而非常见路径。

#### 数据边界澄清（重要）

工具在本地执行，**不等于数据不出设备**——工具的执行结果**仍要回传给模型**才能生成回答。

本地执行的真正收益是：**省上传量、省 token、省延迟**，**不是隐私**。
隐私告知（首次弹窗同意）**仍然必须做**。

#### 成绩明细（已定）

工具**可以返回成绩明细**（如"高数 87 分"），以获得更完整的回答。
代价是明细会发往模型厂商，由首次隐私弹窗统一告知。

#### 必须写进 system prompt 的硬约束

1. **只根据提供的数据回答**；数据里没有的，**明确说"查不到"**，禁止编造。
2. **数值一律由本地算好后再给模型**，禁止模型自行计算。
3. 答不了的问题**不要圆场**，直接说明能力边界。
4. 工具返回空结果时，**如实说明"没查到"**，不要用常识补全。

### 9.3 明确**不做**的 AI 功能

| 功能 | 判断 |
|---|---|
| **今日/明日课程摘要** | **撤回**。纯规则 + 天气 API 更快、免费、100% 准确；用 LLM 反而会**编错教室**并每天烧钱 |
| 课表冲突检测 | 纯规则问题，用 AI 是浪费 |
| 选课建议 | 样本量不足，误导性强，后置 |
| **课表截图导入** | **暂不做**（已定）。教务同步已能解决大部分录入需求。<br>补充：已核实 `deepseek-flash` **支持图像理解**，故此功能的技术门槛与成本比原先估计的低，可作为后续候选 |

> **原则：不要为了 AI 而 AI。** 规则能解决且更准更便宜的，一律不用模型。

### 9.4 依赖社区数据的 AI 功能（等 P2）

- **社区评价摘要**：⚠️ **必须离线批处理，不能实时**。
  错误做法是每个用户打开课程页就调一次（1000 人看同一门课 = 1000 次调用）；
  正确做法是云函数**触发式重算 + 缓存进 `courses.summary`**。
  这把"按用户计费"变成"**按内容计费**"，成本差 2–3 个数量级。
- 二手商品图自动填表（⚠️ 价格建议需谨慎，误导性定价会引发纠纷）
- 学习资料打标签 + 语义搜索（⚠️ 需向量检索，**云开发文档库是否支持要先验证**）

### 9.5 其他必须遵守的技术点

1. **流式输出（SSE）必须做**，否则用户等 5–10 秒无反馈会以为卡死。
2. **降级红线**：**AI 不可用不得影响核心功能**（课表/今日/小组件照常）。
3. **隐私告知**：**首次进入 AI 功能时弹窗**，说明"课表/成绩会发送给你选定的模型服务"，
   同意后方可使用（已定）。
4. **不做多轮上下文无限累积**：限制保留轮数，避免越聊越慢越贵。

### 9.6 跨模块扩展设计（为后续社区模块预留）

> **背景**：后续可能要求 AI 从「二手集市」「美食街」等模块取信息。
> 本节记录为此做的**预留决策**，以及**明确不预留**的部分。

#### 产品定位：只做「组合查询」，不做「替代搜索」（已定）

跨模块 AI 有两种用法，**只做第二种**：

| | 用法 A · 替代搜索 | 用法 B · 组合查询 |
|---|---|---|
| 例子 | "帮我找二手的《编译原理》" | "我这周哪天没课，可以顺路去南区把书交易了" |
| AI 做的事 | 调搜索接口 + 复述结果 | 查课表 + 查集市 + **推理对齐时间** |
| 耗时对比 | 搜索框 3 秒 vs 走 AI 约 6 秒 | 无搜索框可替代 |
| 判断 | ❌ **不做**（搜索能做且更快更准，收益为负） | ✅ **做**（AI 的真正价值） |

**原则**：各模块**必须先把搜索与筛选做好**；AI 只处理「搜索表达不了」的需求——
即**模糊语义**（"便宜点的""适合新手的"）+ **多条件组合**（"50 块以内 + 南区 + 这周能取"）。

#### 必须预留的（3 条，成本低且不会猜错）

| # | 预留项 | 为什么 |
|---|---|---|
| 1 | 工具接口定义成 **`suspend fun`** + 统一结果包装（成功/失败/超时） | 远程工具（读服务器）是**异步、会失败、有超时**的；若只按同步本地函数设计，以后必须重构 `AgentLoop`。**即使本地工具立即返回也照此定义** |
| 2 | 工具**按来源分组**（`ToolGroup`），支持「按上下文只加载某一组」 | 直接决定工具数是否失控（见 §9.2 入口形态） |
| 3 | `ToolSpec`（声明）与 `ToolHandler`（实现）**分离** | 以后新增模块只需加一对，不必改循环 |

#### 明确**不**预留的（现在做会白写）

- ❌ **二手集市/美食街的具体工具签名** —— 模块尚未设计，参数（筛选维度、返回字段）几乎必然要改
- ❌ **美食街/集市的 UI 入口与文案**
- ❌ 任何依赖 `P1` 后端数据的工具实现

#### 数据边界（后续实现时必须遵守）

- 二手集市的**联系方式**、美食街的**定位/打卡记录** —— **不得**作为工具返回值交给模型
- AI 只做**聚合与转述**，不做新论断；摘要**必须标注来源**
  （与 §6.11 课程评价「按维度聚合」同一原则）
- 依赖时序：这部分能力**最早等 P4**（需 P1 后端 + P2 评价先落地）

|---|---|

| 新增 `ScnuInvalidCredentialException` 单独成一类 | 失败锁定**只能**统计「凭据被教务拒绝」。把网络抖动也算进去，用户在信号差的地方点几次就会被锁掉自己的账号 |
| 该异常的判据收紧为「**HTTP 200 + 页面能抠到错误文案**」 | 只按「POST 不是 302」归类的话，SSO 返 5xx/429 也会被记成「用户连续输错」，还可能把用户已保存的密码当成失效删掉。5xx/429/403 属基础设施故障，归普通 `ScnuLoginException` |

| `createUnlockCipher()` 返回 null 时顺手清掉密码 | 密钥因指纹变更被作废时若只返回 null，状态会永远卡在「需要验证身份」，点多少次都失败 |
| 合并登录时**补回**「确认已进入教务系统」校验 | 原 `ScnuScraper.login()` 有 `"jwxt" in finalUrl` 检查，而 `ScnuSsoLogin.login()` 原来直接 `return true`。不补回的话同步链路会失去这层保护，表现为一堆难排查的「JSON 解析失败」 |
| 顺手删除调试页里硬编码的真实学号 | `ScnuVerificationScreen.kt` 原为 `mutableStateOf("202421315041")` —— 开发者本人的学号，源码随仓库分发不该出现 |

## 13. P-AI 方案期补充决策（v1.2 追加，2026-09-23）

> §11 是方案期决策（36 项），§12 是 P0 施工期决策（4 项）。
> 本节记录 **P-AI 开工前**因"跨模块"需求暴露而新增的决策。
> 沿用本文档惯例：**保留被否决的选项与判断依据**。

### 13.1 触发原因：一处设计冲突

用户在 P-AI 开工前提出：「后续可能要求 AI 从『二手集市』『美食街』等模块获取信息」。

**这与已定决策 #18（AI 对话入口放【校园】页）冲突**，原因是：

- 工具清单**每次请求都要塞进 prompt**
- 若 6 个模块 × 3 个工具 = **18 个工具**，会同时导致
  **prompt 变长（每次请求都付费）** 与 **模型选择准确率下降**（工具越多越易选错）
- 而用户站在【校园】页问"有没有便宜的自行车"时，**上下文没有任何线索**提示该加载哪组工具

### 13.2 新增已定（3 项）

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| 41 | **AI 入口形态** | **【校园】页的一个独立模块页**（挂卡片进入，像「教务同步」那样），**不做**每模块内嵌 AI | 与产品整体心智一致（【校园】页 = 功能集合）；用户明确选择 |
| 42 | **跨模块定位** | **只做「组合查询」，不做「替代搜索」**（§9.6 的用法 B） | 用法 A（"帮我找二手的 X"）搜索框 3 秒可完成，走 AI 约 6 秒且可能更不准，**收益为负** |
| 43 | **跨模块预留程度** | **只预留接口**：工具定义成 `suspend` + 统一结果包装 + `ToolGroup` 分组 + `ToolSpec`/`ToolHandler` 分离 | 预留具体工具会白写（模块未设计，参数必改） |

### 13.3 冲突的解法（工具数控制）

对 #18 与"跨模块"的冲突，解法是**按意图路由、只加载命中的工具组**（详见 §9.2）：

- 默认只加载【教务组】（入口在【校园】页，用户最可能问教务）
- 规则命中其他模块 → 换成对应组；命中跨模块 → 加载 2 组
- **工具数始终 ≤ 6**，不随模块数量线性膨胀

> **我的原始建议（被否决，留档）**：我建议改为「每个模块内嵌 AI 入口」，
> 理由是工具集恒定收窄、上下文天然明确（用户站在二手集市页问"有没有便宜的"，无需猜测模块）。
> **用户选择保留全局入口**，并以"意图路由 + 工具分组"作为替代方案。

### 13.4 我的其他提醒（已向用户提出）

1. **AI 替代不了搜索**：二手集市/美食街**必须先把搜索与筛选做好**，
   AI 只做「搜索表达不了」的需求（模糊语义 + 多条件组合）。
   判断标准：**如果用户能用筛选器表达清楚，就不需要 AI。**
2. **工具分两类**：本地工具（读 Room，同步快免费）与远程工具（读服务器，异步会失败）。
   接口现在就要按异步设计（#43）。
3. **数据边界**：集市的联系方式、美食街的定位**不得**交给模型（§9.6）。
4. **时序**：这部分能力**最早等 P4**（依赖 P1 后端 + P2 评价）。
